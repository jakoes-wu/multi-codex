> - 至少有一条绑定时由收敛引擎生成 `codex-auto`，没有绑定时删除；已有名为 `auto` 的账号时判冲突。

## 1. 背景

- 目录绑定已经存在：`bind NAME [DIR]` 把目录的规范路径记进 `config.json` 的 `bindings`（`binding.normalize_dir`，`binding.py:32-47`），`run` 省略账号名时从当前目录向上找最近的绑定（`binding.resolve`，`binding.py:50-59`；`cmd_run`，`cli.py` `cmd_run`）。
- 但要用绑定必须输入 `multi-codex run -- codex …`。当前目录不在任何绑定下时，`run` 直接报错（`cmd_run` 中 `no account is bound to …`）。
- 没有命令能直接回答“这个目录会用哪个账号”，只能看 `bind` 列表里的 `*` 标记（`cmd_bind_list`，`cli.py:1240`）。

## 2. 目标 / 非目标

**目标**

1. 生成 `<bin_dir>/codex-auto`：从当前目录向上找最近的绑定，交给该账号的 `codex-<名称>`；找不到绑定时运行普通 `codex` 并在 stderr 说明。
2. `which [DIR]`：输出该目录会用哪个账号，以及依据。
3. README 补 `run NAME -- codex mcp …` 的示例。

**非目标**

- cd 钩子、改写 shell 配置、让裸 `codex` 自动按目录选账号。
- 项目目录里的标记文件。
- 新的配置字段：沿用现有 `bindings`，不加 `routes` 或默认账号设置（默认账号就是 `~/.codex` 指向的那个，由 `use` 管理）。
- `code`、`app` 按目录选账号。
- `list` 增加绑定或入口命令的显示（`bind` 已能列出）。

## 3. 假设与约束

- **匹配规则与 `run` 一致**：绑定的键是 `normalize_dir` 得到的物理路径（软链已解析、大小写取磁盘上的写法）。`codex-auto` 用 `/bin/pwd -P` 取当前目录的物理路径（`/bin/pwd` 不存在时退回 shell 内建的 `pwd -P`），命中条件是当前目录等于绑定目录，或位于其下（`"$here/"` 以 `"$key/"` 开头）；多条命中时取最长的键。这与 `resolve` 从当前目录逐级向上、遇到第一个键就停的结果相同：越近的祖先路径越长。
- **键为 `/` 时**：`normalize_dir("/")` 得到 `/`，`"$key/"` 会写成 `//`，匹配失败。渲染时对 `/` 单独处理：总是命中，长度记为 1。
- **macOS 大小写**：必须用外部命令 `/bin/pwd -P`，不能用 shell 内建的 `pwd -P`。实测 macOS 的 `/bin/sh`（即 bash）与 bash 的内建 `pwd -P` 按继承来的 `$PWD` 逐段解析，`cd case` 进入实际名为 `Case` 的目录后输出小写 `…/case`；`/bin/pwd -P`、dash 与 Python 的 `os.getcwd()` 都输出磁盘上的 `…/Case`。键在绑定时已改成真实大小写（`binding.py:15-29`），所以 `/bin/pwd -P` 与 `run`（`os.getcwd()` 经 `normalize_dir`）结论一致。macOS 有 `/bin/pwd`；编译机 Ubuntu 20 有 `/bin/pwd`。
- **入口只反映最近一次收敛**：手改 `config.json` 后，到下一次写命令或 `apply` 之前，`codex-auto` 与 `run` 可能不一致；`doctor` 的漂移检查会报出。
- **绑定指向未登记账号**（悬空绑定，`doctor` 的 bindings 检查会报）：`run` 在最近的绑定悬空时报错退出 1，不继续向上找。`codex-auto` 保持同样语义：最近的命中是悬空绑定时，输出同样的报错并退出 1。
- **入口命令用绝对路径调用** `<bin_dir>/codex-<名称>`，不经 `PATH` 查找，免得被同名文件遮住。目标账号的启动命令负责代理、隔离变量与环境变量，`codex-auto` 本身不设置任何环境。
- **没有绑定时运行 `codex`**：用户已在 shell 里配置的 `CODEX_HOME` 等仍会生效（与直接运行 `codex` 完全相同）；提示写 stderr，不影响 stdout。
- **受管标记**：`# managed-by: multi-codex router`。它不以 `account=` 开头，`launcher.managed_account`（`launcher.py:127-140`）返回 None，所以 `scan_managed` 不会把它当成账号启动命令，`apply` 的孤儿清理也不会删它。
- **`which` 是只读命令**：不加锁，未完成的迁移或 restore 不拦（同 `list`、`path`）。

## 5. 方案

### 5.1 实现要点

#### 5.1.1 `router.render(config)`

```sh
#!/bin/sh
# managed-by: multi-codex router
# Generated by multi-codex from directory bindings. Do not edit; use `multi-codex bind` / `unbind`.
here=$(/bin/pwd -P 2>/dev/null || pwd -P) || exit 1
best=0
target=''
stale=''
# 每条绑定一段（按键排序，内容稳定）：
case "$here/" in
  '/Users/x/work'/*)
    if [ 14 -gt "$best" ]; then best=14; target='/Users/x/.local/bin/codex-work'; stale=''; fi ;;
esac
# 悬空绑定：target 为空，stale 记下报错文字
case "$here/" in
  '/Users/x/old'/*)
    if [ 13 -gt "$best" ]; then best=13; target=''; stale='account gone bound to /Users/x/old is not registered; run: multi-codex unbind /Users/x/old'; fi ;;
esac
if [ -n "$stale" ]; then
  printf 'multi-codex: %s\n' "$stale" >&2
  exit 1
fi
if [ -n "$target" ]; then
  if [ ! -x "$target" ]; then
    printf 'multi-codex: launcher %s is missing; run multi-codex apply\n' "$target" >&2
    exit 1
  fi
  exec "$target" "$@"
fi
printf 'multi-codex: no account is bound to %s or its parents; running codex (the default account)\n' "$here" >&2
if ! command -v codex >/dev/null 2>&1; then
  echo "multi-codex: codex not found in PATH" >&2
  exit 127
fi
exec codex "$@"
```

- 每段的长度是键在 Python 里算出的字符数（`len(key)`），写成字面数字，不在 sh 里用 `${#var}`：键可能含多字节字符，`${#var}` 在不同 shell 里按字节还是按字符计不一致。比较的只是同一组键之间的相对长短，按字符计足够；同一路径链上的祖先键一定是后代键的前缀，字符数一定更少。
- 所有路径与文字经 `shlex.quote` 或 `printf '%s'` 输出，不经 shell 展开。悬空绑定的报错文字用 `shlex.quote` 写成单引号字面量，且不含反引号与 `$`：单引号里出现它们会触发 shellcheck SC2016（info 级，退出码 1）。
- 绑定目录名本身含 `$` 或反引号时，单引号里的它们仍会触发 SC2016（只影响 shellcheck，运行无影响）；T16 使用不含这两个字符的目录名。
- 实测（bash、dash、zsh、ksh 与 macOS `/bin/sh`）：`shlex.quote` 加引号后，键里的 `*`、`?`、`[x]` 在 case 模式中按字面匹配，空格、单引号、非 ASCII 也正常；不含特殊字符的键 `shlex.quote` 不加引号，同样安全。
- 键为 `/` 时该段写成无条件命中：`if [ 1 -gt "$best" ]; then …; fi`。
- 目标启动命令路径为 `launcher.launcher_path(expand(config.bin_dir), account.name)`，账号名取 `config.find(...)` 的实际大小写。
- 报错含义与 `cmd_run` 一致（`no account is bound to …`、`account … bound to … is not registered`），前缀不同：sh 是 `multi-codex:`，Python 是 `[multi-codex] error:`；没有绑定时多一句 `running codex (the default account)`。
- 目标启动命令不存在或不可执行时（`[ -x "$target" ]` 为假），输出 `multi-codex: launcher … is missing; run multi-codex apply` 并退出 1，而不是让 `exec` 报 not found。

#### 5.1.2 收敛计划

在 `accounts.plan` 计算 `config_changed`（`accounts.py:124`）之前追加，`P = router.router_path(new_bin)`：

1. **是否启用**：`new.bindings` 非空。
2. **名称冲突**：启用且 `new.find("auto")` 不为 None 时（按 casefold 比较，Linux 上的 `Auto` 也算），追加 `CONFLICT launcher P`，原因 ``codex-auto is generated from directory bindings; rename the account named 'auto' (multi-codex rename auto NEW) or remove the bindings``。
3. **入口文件**（启用、且没有第 2 条冲突时）：
   - `P` 不存在，或 `P` 就是本次计划要删除的某个文件（例如 `rename auto x`、`remove auto`、`restore auto` 时，名为 auto 的账号的启动命令正被删除）→ `CREATE`。删除动作排在前面执行，顺序正确。“就是同一个文件”按文件身份判断：`os.path.samestat(os.lstat(P), os.lstat(q))` 对 `planned_deletes` 中任一路径 q 成立。不能按字符串比较：macOS 上账号 `Auto` 的启动命令路径是 `…/codex-Auto`，与 `P`（`…/codex-auto`）字符串不同却是同一个文件；也不能按 casefold 比较文件名：Linux 上 `codex-Auto` 与用户自己的 `codex-auto` 是两个文件，误判会覆盖用户文件；
   - `router.is_router(P)` 为真 → 内容相同且可执行为 `UNCHANGED`，否则 `UPDATE`；
   - 其它（用户自己的文件、软链、目录、账号启动命令）→ `CONFLICT`，原因 `already exists and is not the multi-codex router`。
4. **未启用**：`router.is_router(P)` 为真 → `DELETE`，原因 `no directory bindings`；否则不动。
5. **`bin_dir` 变化**：旧 `bin_dir` 下的受管入口 → `DELETE`，原因 `bin_dir changed`（与账号启动命令相同的处理，`accounts.py:98-100`）。
6. 写文件复用 `_write_launcher`（`accounts.py:194`），模式 0755（入口不含密钥）。判断“内容相同”复用 `launcher.launcher_file_ok(path, content, None)`。

所有走收敛的写命令都会更新入口：`bind` / `unbind`（增删绑定）；`rename`（改写绑定里的账号名，`cli.py` `_rename_config`，入口目标随之 UPDATE）；`remove`、`restore`、`apply -f`（`binding.drop_account` 去掉绑定）；`add` / `migrate-default`（让悬空绑定变为有效）；`init --bin-dir`（第 5 条）。`doctor` 的漂移检查调用 `plan`（`doctor.py:55`），入口与配置不一致时同样报出。

#### 5.1.3 `which [DIR]`

```text
multi-codex which [DIR]
```

- DIR 缺省为当前目录；不是目录时 `error("not a directory: …")`，退出 1。
- 配置不存在或没有命中绑定：stdout 输出 `switch.describe_default(config)[1]`（与 `use` 不带参数的输出相同，例如 `work`；以 `(` 开头的如 `(none)`、`(not migrated: …)` 表示没有已登记的默认账号），stderr `hint("no binding for {目录}; plain codex uses the default account")`；shell 里设了 `CODEX_HOME` 时再提示一句 `CODEX_HOME is set in this shell, so plain codex uses {值} instead`，退出 0。
- 命中且账号已登记：stdout 输出 `config.find(name).name`（登记时的大小写），stderr `print("[multi-codex] bound to {绑定目录}", file=sys.stderr)`（与 `cmd_run` 的写法一致；`actions.info` 写 stdout，不能用），退出 0。
- 命中但账号未登记：`error("account {!r} bound to {} is not registered; run `multi-codex unbind {}`")`，退出 1（与 `run` 相同）。
- stdout 只有账号名或默认账号说明一行，便于脚本读取。

#### 5.1.4 `restore` 搬数据前预检冲突

`restore` 先移动数据、最后才收敛注销（`switch.py:257-278`），收敛冲突会停在“数据已回到 ~/.codex、注销失败”的半完成状态（`switch.py:280-284`）。本方案新增的名称冲突会让这种情况更容易出现（已有 `auto` 账号与绑定时 restore 其它账号）。所以在 `restore_account` 的 `dry_run` 判断之前（`switch.py:244`），只在状态 A（还没写 restore 标记、数据没动）时，先用“注销该账号之后”的新配置调用 `accounts.plan`，参数与 `switch.py:278` 的 `converge` 相同（同一个 `new`、`config_exists`、`orphan_scope={canonical}`）；有冲突就像 `migrate.py:273-280` 那样逐条 `error(..., phase="precheck")` 并退出 3，什么都不动。A2、B、C 已写了标记（B、C 时数据已动），维持原行为：进入它们之前在状态 A 已经通过预检，之后配置被标记锁住，一般不会出现新冲突。`--dry-run` 也会报出冲突。预检时账号目录还在，`shared.plan_remove_links` 只产生 DELETE，不会造成“预检拦下、实际能过”的分歧。`doctor` 的漂移检查调用 `plan`（`doctor.py:55`），入口与配置不一致时同样报出。

## 6. 备选方案与决策

- **`codex-auto` 调用 `multi-codex run`**：每次启动多一个 Python 进程，且依赖 `multi-codex` 在 `PATH` 中；纯 sh 与账号启动命令的做法一致。不采用。
- **新增路由规则与默认账号配置（`route` 子命令）**：与已有的 `bind` 重复。不采用。

## 7. 影响分析

**正向**

- **收敛计划**：只在末尾多几个动作；没有绑定且没有旧入口时不产生任何动作，现有用例的输出不变。
- **`bind` / `unbind`**：第一次 `bind` 会多一行 `create launcher …/codex-auto`；最后一次 `unbind` 多一行 `delete launcher …/codex-auto (no directory bindings)`。`unbind` 打印的 `binding_change` 行（`cli.py` dispatch 末尾）不受影响。
- **`apply`**：有绑定的配置在新机器上 `apply` 时会生成 `codex-auto`。
- **`which`**：只读。

**反向**

- **孤儿清理**：`scan_managed` 不认路由标记，入口不会被当成孤儿删除；路由计划只认路由标记，不会删账号启动命令。
- **名为 `auto` 的账号**：没有绑定时一切照旧；有绑定时 `add auto`、`bind` 等写命令都判冲突（退出 3，什么都不写），报错提示 `rename auto NEW` 或删除绑定。`rename auto x`、`remove auto`、`restore auto` 本身不冲突：它们删掉 auto 的启动命令后，入口在同一次收敛中重建（§5.1.2 第 3 条）。已有 auto 账号与绑定的 v0.9 用户升级后，写命令会被这条冲突挡住，直到改名或解绑；CHANGELOG 写明。
- **`restore` 的搬数据顺序**：§5.1.4 的预检让收敛冲突在搬数据之前报出；数据已搬（状态 C）的续跑路径不变。预检只调用只读的 `plan`，不改任何文件。
- **`doctor`**：漂移检查会报出缺失或过期的入口，修复建议沿用 `multi-codex apply`。
- **`remove`**：删账号会去掉它的绑定；若这是最后一条绑定，入口随之删除。

**运行时**：`codex-auto` 每次启动做 1 次 `/bin/pwd -P`（一个子进程）与 N 次 `case` 匹配（N 为绑定数），开销可忽略。

**部署形态**：`codex-auto` 是 POSIX sh，与账号启动命令同样只在 macOS 与 Linux 上生成。

| T3 | 在 `<dir>` 及其子目录运行 `codex-auto x` | 假 codex 收到参数 `x`，`CODEX_HOME` 为 work 的目录（经 work 的启动命令，隔离变量被清除） |
| T3b | macOS 大小写不敏感文件系统（复用 `tests/test_binding.py:18` 的 `case_insensitive` 判断）：绑定 `<dir>/Case` 后 `cd` 进 `<dir>/case` 运行 `codex-auto` 与 `run` | 两者都用该账号 |
| T4 | 嵌套绑定：`<dir>` 绑 work、`<dir>/sub` 绑 home | 在 `<dir>/sub/deeper` 运行用 home；在 `<dir>` 运行用 work；与 `run` 的选择一致 |
| T5 | 没有命中绑定的目录运行 `codex-auto` | 运行普通 codex（`CODEX_HOME` 不被设置），stderr 含 `no account is bound to` 与 `default account` |
| T6 | 绑定目录名含空格、单引号、非 ASCII、`*`、`?`、`[` | 正常命中；兄弟目录（如绑 `a*` 时的 `ab`、绑 `a?b` 时的 `axb`）不命中 |
| T6b | 绑定 `/` 到 A、某子目录到 B | 在子目录下用 B，在其它目录用 A |
| T7 | 通过软链进入绑定目录 | 命中（`pwd -P` 解析软链） |
| T8 | 悬空绑定（手写配置中绑定指向未登记账号）最近命中，且更外层有有效绑定 | 退出 1，stderr 含 `is not registered` 与 `multi-codex unbind`；`run` 给出同样结论 |
| T8b | 被绑定账号的启动命令被删除后运行 `codex-auto` | 退出 1，stderr 含 `is missing` |
| T9 | 最后一次 `unbind` | 删除 `codex-auto`，原因 `no directory bindings` |
| T10 | 已有名为 `auto` 的账号时 `bind work <dir>`；有绑定时 `add auto` | 都退出 3，冲突原因含 `multi-codex rename auto`，配置与文件系统不变 |
| T10b | 手写配置造出“账号 auto + 绑定”后，分别 `rename auto x`、`remove auto`、`restore auto`（`use auto` 之后） | 都成功，最后 `codex-auto` 是路由入口 |
| T10f | 大小写不敏感文件系统上账号 `Auto` 加绑定，`rename Auto x` | 成功，`codex-auto` 是路由入口；区分大小写的文件系统上跳过 |
| T10c | 同上配置下 `restore` 另一个账号 | 退出 3，冲突在搬数据之前报出：`~/.codex` 与账号目录都不变，没有 restore 标记 |
| T10d | `rename work job`（work 有绑定） | `codex-auto` 内容改为指向 `codex-job`；`run` 也用 job |
| T10e | `remove work`（唯一绑定指向 work）；`apply -f` 删掉 work；`add` 让悬空绑定变有效 | 前两者删除 `codex-auto`；后者生成 |
| T11 | `codex-auto` 是用户自己的文件时 `bind` | 退出 3，原因 `not the multi-codex router`，文件不变 |

| T13 | `apply` 的孤儿清理 | 不删除 `codex-auto`；`apply` 之后为 already up to date |

## 9. 日志 / 观测点

- 收敛动作：`create|update|delete launcher …/codex-auto (…)`，冲突原因见 §5.1.2。
- `codex-auto` 的 stderr：`multi-codex: no account is bound to … or its parents; running codex (the default account)`、`multi-codex: account … bound to … is not registered; run multi-codex unbind …`。
- `which`：stdout 一行账号名或默认账号说明；stderr `bound to …` 或 `hint: no binding for …`。
